# マスタ名称の大小文字を区別しない一意性を DB で担保する

`catalogs.name` と `locations.name` の unique index に照合順序を指定せず、大小文字の違いをアプリケーション層のバリデーションのみで扱う。DB レベルでは大小文字を区別したままとする。

## なぜスコープ外なのか

`Catalog` と `Location` はどちらも `validates :name, uniqueness: { case_sensitive: false }` を宣言している一方、対応する unique index には照合順序の指定がない。したがって並行リクエストがバリデーションのタイミングをすり抜けると、DB は `"Bento"` と `"bento"` の両方を受け入れる。この不整合自体は事実である。

`employees.username` はカラムレベルで `collation: "NOCASE"` を指定しており、同じ手法を適用すれば整合は取れる。それでも見送るのは次の理由による。

### SQLite の NOCASE は ASCII しか畳まない

`NOCASE` が同一視するのは `A`–`Z` と `a`–`z` だけである。カタログ名も販売先名も日本語で登録される。

```
日替わり弁当A / 日替わり弁当a   ← NOCASE が守れるのはこの末尾 1 文字だけ
市役所 / 市役所                  ← 元から同一。NOCASE は無関係
```

`employees.username` は `format: { with: /\A[a-zA-Z0-9_]+\z/ }` で ASCII に限定されているため NOCASE が完全に機能する。マスタ名称にはその前提がない。同じ手法に見えて、得られる保護の範囲がまったく違う。

### 守るべきレースが実質的に発生しない

このアプリケーションは小さなお弁当屋さんの出張販売を支援するものであり、商品マスタと販売先マスタの登録は店主が単独で行う。「2 人が同時に、ASCII の大小文字だけが異なる同名マスタを登録する」という競合は業務上まず起こらない。既存のモデルバリデーションが通常経路を押さえている。

### 対処のコストが保護に見合わない

SQLite にはカラムの照合順序を後から変更する `ALTER TABLE` がない。Rails の SQLite3 アダプタは `change_column` を内部でテーブル再作成に展開する（一時テーブルへコピー → 元をドロップ → 元の名前で復元）。`catalogs` は 6 本の外部キーから参照されており、このスキーマ変更の中では最もリスクが高い部類にあたる。

インデックスレベルで `COLLATE NOCASE` を指定する代替案もあるが、こちらは生 SQL の `execute` が必要で `schema.rb` に往復できない。採用すれば `schema_format` を `:sql` へ移行することになり、影響がスキーマ運用全体に及ぶ。

### 判断が変わる条件

以下のいずれかが起きたら再検討する価値がある。

- マスタ登録を複数人が並行して行う運用になる
- カタログ名や販売先名に ASCII 英字の比重が増える（英語表記の商品を扱う等）
- 大小文字違いの重複マスタが実際に本番データで発生する
