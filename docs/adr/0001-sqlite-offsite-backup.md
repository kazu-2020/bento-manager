# ADR-0001: SQLite のオフサーバーバックアップ戦略

- **状態**: 承認
- **日付**: 2026-08-13
- **関連 Issue**: [#247](https://github.com/kazu-2020/bento-manager/issues/247)

## 背景

本番の売上データは単一の VPS 上の Docker named volume (`bento_manager_storage`) にのみ存在し、サーバー障害でデータが全損する。`config/deploy.yml` のコメント自身にも "backed up off server" の推奨があるが未対応だった。

売上台帳という性質上、これは運用上の最優先課題である。

前提となる環境:

- 単一 VPS（冗長性なし）、Kamal 2 でデプロイ
- 本番 SQLite は primary / cache / queue / cable の 4 本
- Active Storage は未使用。`storage/` の中身は実質 SQLite ファイルのみ
- 顧客の個人情報は保存していない（`sales` は区分と金額のみ、`employees` は username と password_hash のみ）
- Sentry と 1Password は既に本番運用に組み込まれている
- 運用者は 1 名

## 決定

### 1. 継続レプリケーション（Litestream）を採用する

RPO は数秒。定期スナップショット方式（cron + オブジェクトストレージ転送）は採らない。

**理由**: 精度の要求ではなく運用コストの問題。定期スナップショット方式には「バックアップが失敗していたことに誰も気づかない」という古典的な問題があり、失敗検知を自前で作る必要がある。年間数 MB オーダーのデータ量では、秒単位にしても転送量もストレージ代も実質変わらない。安い方がたまたま高精度というケースだった。

### 2. 保存先は AWS S3 (`ap-northeast-1`)

**理由**: 既にアカウントを保有しており、請求先と管理画面を増やさないことの価値が月数十円の差を上回る。

どの AWS アカウントに置くかは本 ADR では決めていない。[ADR-0002](0002-backup-infrastructure.md) で専用アカウント `bento-manager` (394123064455) を新設すると決定した。

Cloudflare R2 は当初の候補だったが却下した。Litestream 公式ドキュメントに既知の不具合として名指しされている — `DeleteObjects` が HTTP 200 と「削除済み」を返すのに実際にはファイルが消えない silent failure。回避策は R2 側の Object Lifecycle ルールだが、それは保持期間の制御がリポジトリの外へ逃げることを意味する。1 人運用で事故は忘れた頃に起きる以上、コードに残らない設定は負債である。

### 3. Litestream は Kamal accessory（独立コンテナ）として動かす

app コンテナに同梱する `-exec` 方式は採らない。既存の named volume を `volumes:` で共有し、実行ユーザーは app コンテナと同じ uid 1000 に揃える。

**理由**: `-exec` には「Litestream が起動できなければ Rails も起動しない = バックアップ停止が必ず表面化する」という強い利点がある。それでも accessory を選ぶのは、`-exec` が「バックアップが壊れたら店が売上を記録できなくなる」ことを意味するため。**バックアップを 1 日失うのは復旧可能だが、営業中に POS が上がらないのは復旧不能**であり、障害の重み付けが釣り合わない。加えて accessory なら `kamal deploy` 中もレプリケーションが途切れない。

**引き受けた負債**: accessory は `kamal deploy` の対象外であり、設定変更は `kamal accessory reboot litestream` を明示的に叩くまで反映されない。また Litestream が死んでも Rails は動き続けるため、失敗検知を別途用意する必要がある（決定 5 で返済）。

### 4. バックアップ対象は `production.sqlite3` のみ

cache / queue / cable は対象外とする。

**理由**: 容量の節約ではなく、復旧手順を「1 ファイルを戻すだけ」に単純化するため。3 本は `bin/docker-entrypoint` の `db:prepare` で作り直される。

より重要な理由として、queue DB は仕事がゼロでも Solid Queue のハートビート書き込みが定常的に発生する。これを対象に含めるとレプリケーショントラフィックの大半が復旧価値ゼロのデータで占められ、決定 5 の監視において「うるさい方の健全さ」に紛れて肝心の primary の停止を見逃す。**監視対象は守りたいものと一致していなければならない。**

**将来ジョブ機能を使う場合の想定**: 定期タスクは `config/recurring.yml` から起動時に再登録されるため失われない。失敗記録は Sentry に複製済み。前提は「ジョブは primary から再導出できる作業の実行手段であって、作業が必要だという事実の記録場所ではない」こと。**この前提が崩れるのは、ジョブが primary のどこにも存在しない情報を抱える場合**（例: 単発の予約通知で、その日時が queue DB にしか無い）。ただしその場合の正しい対処は「バックアップ対象を増やす」ではなく「その予定を primary のテーブルに持たせる」ことである。キューを business intent の唯一の保管場所にするのは、バックアップ以前に設計として脆い。

### 5. 失敗検知は日次のリストア訓練で行う

`litestream restore` を一時パスに実行して検証し、結果を Sentry Cron Monitor にチェックインする。`litestream` バイナリは app イメージにも同梱し、本番リストアの実行手段を兼ねる。

**理由**: 決定 4 と同じ原則の適用。守りたいのは「プロセスが動いていること」でも「S3 にオブジェクトがあること」でもなく「事故ったときに実際に戻せること」であり、代理指標には必ず「指標は緑なのに実物は壊れている」隙間ができる。

Prometheus メトリクス方式を採らない理由: Litestream には**「最後に同期に成功した時刻」に相当するメトリクスが存在せず**、カウンタの増分を自前で追う状態付きの監視になる。加えて公式に「sync retry backoff ループに嵌まる」失敗モードが記載されており、**この状態ではプロセスは生きていてメトリクスも応答する**ため、プロセス監視では検知できない。

### 6. 訓練の合格条件は integrity_check + 本番との一致検証

`PRAGMA integrity_check` に加え、復元したコピーと本番 DB の状態（`sales` の最大 id と件数を軸とする）が一致することを確認する。検証中にも売上が入りうるため、厳密一致ではなく「復元側が本番以下、かつ差が一定範囲内」で判定する。

**理由**: `integrity_check` だけでは、レプリケーションが 3 週間前に止まっていても「3 週間前の完全に健全な DB」が復元されて緑を返し続ける。

一方で「復元した DB の最新の売上が十分新しいこと」を条件にすると、**店が休みの日に必ず失敗する**。出張販売は毎日あるとは限らず、「データが古い」は正常な状態である。業務データの新しさを健全性の指標に使ってはならない。

「本番と一致しているか」を見れば、営業日はレプリカが止まれば即座に不一致となる。

**ただし売上だけを比べると、静止期間中は何も検証していないのと同じになる。** 休業日は本番も止まるため両者が自明に一致し、判定は `integrity_check` だけに退化する。金曜の夜にレプリケーションが死ぬと、土日と月曜の訓練はすべて緑を返し、検知は火曜まで遅れる。出張販売は毎日あるとは限らない以上、この静止期間は数日から数週間に伸びうる。「1 日以内に検知する」という要求を満たさない。

そこで訓練自身が本番に 1 行書き（`backup_heartbeats`）、**その鼓動が復元側に現れることを 3 番目の条件とする。** 訓練は業務と無関係に毎日走るので、店が休みでも鼓動は増える。複製が止まればその翌日には食い違う。

条件は「**前回の訓練の鼓動が復元側に入っていること**」とする。今回書いた分は復元の時点でまだ S3 に届いていないことがあるため条件にしない。件数の差で見る形にはしない。それだと「訓練は 1 日 1 回・1 行だけ書く」という別クラスの実装事実とスケジュールに許容値が依存し、実行頻度を変えた瞬間に、複製が健全なまま訓練だけが赤くなる。

**レプリカ側のメタデータの鮮度（最新 LTX のタイムスタンプ等）は採らない。** Litestream はアイドル時に LTX を生成しないため、休業日に必ず誤検知する。仮にバージョンによってアイドル時も書き込むとしても、それは保証された挙動ではなく、依存すると次の更新で静かに壊れる。加えて「S3 にオブジェクトがあること」は決定 5 が代理指標として退けた対象そのものである。カナリアなら app の書き込みから復元までの経路全体を通しで検証できる。

### 7. 保持期間は 30 日

`snapshot.retention` と `levels` を明示的に設定する（Litestream v0.5 のデフォルトは 24 時間）。

**理由**: 守るべきは**「壊れたデプロイ」** — マイグレーションのバグでデータが欠損・変形し、日次の集計を見て初めて分かるシナリオ。気づくまでに数日から数週間かかりうるため、デフォルトの 24 時間では気づく前に窓が閉じる。

**入力ミスの訂正はバックアップの仕事ではない。** このアプリは `sales.voided_at` / `corrected_from_sale_id` / `refunds` で訂正を扱う設計であり、それをバックアップで巻き戻すのは訂正履歴という監査上重要な記録を消すことになり有害である。

1 年以上の保持も採らない。その動機はおそらく税務・帳簿の保存であり、**DB のバックアップではなく帳票出力機能で解くべき別要件**。バックアップに背負わせると「バックアップが法定保存の代替である」という誤った前提が運用に埋め込まれる。

### 8. 復旧手順はサーバー全損からの再構築までを対象とする

RTO は「一晩」（翌朝の出張販売に間に合う）。自動フェイルオーバーの類は採らず、コピペで完走できるコマンド列として手順書を残す。

**理由**: #247 の出発点は「サーバー障害でデータが全損する」ことだった。その障害を想定して秒単位のレプリケーションを入れておきながら、復旧手順が「サーバーは生きている前提」では、一番備えたかったケースで手が止まる。

現状リポジトリにはサーバー構築手順が一行も残っておらず、全損時に頼れるのは運用者の記憶だけである。これは実質的にバックアップの不在より弱い環だった。

なお、レジストリが `registry.server: localhost:5550` でサーバー側に同居しているため、全損時はレジストリの再構築も手順に含まれる（イメージはソースから再ビルドできるのでデータ損失ではない）。

### 9. S3 バケットはバージョニング + ライフサイクルで保護する

非現行バージョンの保持期間は 30 日（決定 7 と揃える）。IAM は当該バケット・当該プレフィックスのみに限定した専用ユーザーとする。

**理由**: 本番サーバーの中にバックアップを削除できる認証情報が置かれる。サーバー侵害だけでなく、設定ミスや `kamal accessory` の操作ミスでも、守りたかったデータごと消えうる。バックアップ元と保存先が同じ鍵で繋がっている状態を放置しない。

Object Lock (WORM) は採らない。Litestream は compaction と保持期間管理のために日常的にオブジェクトを削除するため、削除を禁止すると**その削除が恒常的に失敗し続ける**。オブジェクトは溜まり続け、ログはエラーで埋まる。守りを固くしたつもりで決定 5 の監視を壊すことになる。

## 決定不要として閉じた論点

- **保管時の暗号化**: S3 は 2023 年以降すべての新規オブジェクトに SSE-S3 (AES256) をデフォルト適用するため、決定 2 の時点で充足される。クライアント側暗号化は「鍵を失った瞬間にバックアップも失う」新たな単一障害点を作ることになり、この機密性のレベルに対して割に合わない。

## 影響

- app イメージに Litestream バイナリ（Go 静的バイナリ）が加わり、十数 MB 増加する
- VPS 上の常駐コンテナが 1 つ増える
- 日次のリストア訓練が本番サーバーの CPU とディスクを使う（DB が数 MB のため実質無視できる）
- `litestream.yml` の変更時は `kamal accessory reboot litestream` が必要（決定 3 の負債）
