# ADR-0008: ヒートマップの濃淡は消化率で塗り、残数 0 の日には別の印を足す

- **状態**: 承認
- **日付**: 2026-08-22
- **関連 Issue**: [#407](https://github.com/kazu-2020/bento-manager/issues/407)
- **関連**: [ADR-0006](0006-bento-sales-history-counts-bento-lists-everything.md)

## 背景

弁当販売履歴のヒートマップは、月内の販売個数を並べて 20 / 40 / 60 / 80 パーセンタイルで区切り、その順位で濃さを決めていた。ADR-0006 で数える単位を金額から個数に替えたあとも、この相対スケールはそのまま残っていた。

**相対スケールには 2 つの問題がある。**

ひとつは、月ごとに基準が動くこと。同じ 24 個の日が、よく売れた月には薄く、売れなかった月には濃く塗られる。月を送って見比べるための画面なのに、月をまたいだ比較ができない。

もうひとつは、値の幅が狭い指標で差が増幅されること。1 日 20〜30 個の商いでは、月内の最小と最大がせいぜい 10 個しか離れない。パーセンタイルはその 10 個の幅を最薄から最濃まで引き伸ばすので、業務上ほとんど差のない 2 日が正反対の濃さで並ぶ。

**そして、濃淡が何を答えているのかという問題がある。**

積込数を決めるために見たいのは「積んだ分がどれだけ捌けたか」であって、絶対的な個数ではない。20 個積んで 20 個売れた日と、30 個積んで 24 個売れた日では、前者のほうが積み方として際どい。ところが個数で塗ると後者のほうが濃くなる。

その際どさの正体は残数 0 である。**消化率 100% は売り切ったことではなく、残数が 0 になった、つまり買いに来た客を逃した可能性がある日を意味する**（`CONTEXT.md` の「残数」「消化率」）。消化率で塗ると、この日は当然いちばん濃く出る。濃淡だけを見れば「最もよく売れた日」であり、警告として読める手がかりがない。

## 決定

**濃淡は消化率で塗る。閾値は月に依らない固定値とする。**

```text
0.5 / 0.7 / 0.85 / 0.95
```

等間隔（20% 刻み）にしない。適正残数は 2〜3 個であり、1 日 20〜30 個の商いでは目標どおりに終えた日の消化率が 90% 前後に集まる。等間隔で切ると大半が最濃に潰れ、目標どおりの日と積みすぎた日を読み分けられない。**濃淡の解像度は、判断が分かれる帯域に置く。**

**残数 0 の日には、濃淡とは別の印を足す。**マスの右上に小さな警告色の丸を出す。濃淡の意味は「よく売れた」のまま動かし、そのうえで「ただしこの日は客を逃したかもしれない」を重ねる。**ひとつの視覚チャネルに 2 つの意味を負わせない。**

**弁当を 1 個も積まなかった日には色をつけない。**分母が 0 で消化率が定まらないため、0% として薄く塗るのも 100% として印を付けるのも嘘になる。`Sales::HistoryCalendar#daily_sell_through` はこの日をキーごと落とし、率が「無い」ことを nil ではなく不在で表す。

**マスに出る数字は販売個数のまま**とする。濃淡が率を、数字が量を答える。

### 積んだ総数は残数から復元する

消化率の分母は「その日に積んだ弁当の総数」であり、これはどこにも保存されていない。`daily_inventories.stock` は販売のたびに減るので、日が終わった時点の値は残数である。

当日在庫は登録・在庫訂正・追加発注でしか増えず、確定した販売でしか減らない。したがって**残数に確定した販売数を戻せば、積んだ総数になる**。在庫訂正は販売開始前にしか行えないため訂正で宣言された個数はそのまま残数と販売数に分かれ、追加発注はその場で当日在庫に加わる。取り消された販売は在庫が戻るので残数の側に含まれ、分子からも分母からも二重に数えられない。

## 検討して採らなかった案

- **相対スケールのまま、区切りを緩める** — 月ごとに基準が動く問題は残る。月送りで見比べる画面である以上、これが本題である。
- **消化率 100% の日を最濃から外す（たとえば警告色で塗る）** — 濃淡の意味が「よく売れた」から「よく売れた、ただし 100% を除く」に変わる。凡例が説明できなくなるうえ、96% と 100% の日が並んだときに前者のほうが濃く見える。
- **マスの数字を消化率にする** — 何個売れたかは積込数を決める最初の材料であり、率だけでは「30 個積んで 90%」と「10 個積んで 90%」が同じに見える。量と率は両方要る。
- **弁当を積まなかった日を 0% とみなす** — 見た目はどちらも色なしで変わらないが、モデルが持つ値としては別のことを主張してしまう。0% は「積んだのに売れなかった」という事実であり、分母が無い日はそれを言えない。率が定まらないことを 0 でも 1 でもなく不在で表さないと、率を読む側が全員この区別を自前で書く羽目になる。

## 結果

- **ADR-0006 の「弁当 0 個の日をヒートマップの濃淡の閾値から外す」は不要になった。**閾値が月内の分布から計算されなくなったため、外すべき母数そのものが無い。0 個の日は消化率 0% として色がつかないだけで、他の日の濃さには一切影響しない。「1 日平均は 0 個の日を数えるのに濃淡は数えない」という母数のねじれも消えた。
- **月をまたいで同じ濃さが同じ売れ方を指す。**月送りでの比較が成り立つ。
- **色のついたマスの多くが濃い側に寄る月がありうる。**目標どおりに商えている月ほどそうなる。バグではない。
- **積んで 1 個も売れなかった日と、そもそも弁当を積まなかった日は、どちらも色なしで並ぶ。**前者は消化率 0%、後者は率そのものが無いという別の状態だが、ADR-0006 が「弁当 0 個の日には色をつけない」と決めている以上、濃淡では区別しない。区別は率を読む側（モデルの返り値）で保つ。
- 消化率は `daily_inventories` を読むため、弁当販売履歴の集計対象が `sales` だけではなくなった。**弁当の在庫行が残っていない日は、消化率を持たない日として色も印もつかない。**残数 0 とみなすと分母が販売数と一致して必ず 100% になり、積んだ数が分からないだけの日を「客を逃した日」として名指ししてしまう。`lib/tasks/sample_data.rake` は当日分の当日在庫しか作らないため、開発環境の過去日はすべてこの状態になる。
- **`Sale#void!` を `Sales::Refunder` の外から呼ぶ経路が生えると、分母が静かに過小になる。**取消は在庫の復元とセットで初めて「残数 + 確定販売数 = 積んだ総数」を保つ。復元を伴わない取消を足すと、その日は偽の残数 0 として印がつく。
